# Tool-Calling Loop

A minimal, hand-written tool-calling loop against the Gemini Interactions API. The model answers questions about power-grid substations by calling two local Python functions. The loop is written by hand instead of using the SDK's automatic function calling, so every step is visible: what gets sent, what the model asks for, what the tools return, and how the history grows. With `store=False` the server keeps nothing between requests, and all conversation state lives in a Python list.

## What it does

1. Read a prompt from stdin and put it in a `history` list as a `user_input` step.
2. Send the whole `history`, plus the tool definitions, to the model.
3. Append every step the model returns (thought signatures, function calls, text) to `history`.
4. If the model asked for functions, run each one locally and append a `function_result` step whose `call_id` matches the call's `id`.
5. Repeat until the model replies without asking for a function, then print its answer.
6. Every request, response and tool result is printed as JSON.

## Setup

Requires Python 3.11+.

```bash
# with uv
uv sync

# or with pip
python -m venv .venv && source .venv/bin/activate
pip install google-genai python-dotenv
```

Create a `.env` file in the project root (it is git-ignored):

```
GEMINI_API_KEY=your-key-here
```

Run it and type a question when prompted:

```bash
uv run main.py
```

## Example

Prompt: `whats the load on Neuenhagen`. Output is trimmed, with thought signatures shortened:

```
===== TURN 1: REQUEST HISTORY (1 steps) =====
[{"type": "user_input", "content": [{"type": "text", "text": "whats the load on Neuenhagen"}]}]

===== TURN 1: RESPONSE STEPS =====
[{"type": "thought", "signature": "EqoE..."},
 {"type": "function_call", "name": "get_substations", "arguments": {"name": "Neuenhagen"}, "id": "call_160517"}]

===== TURN 1: RAN get_substations =====
{"type": "function_result", "call_id": "call_160517",
 "result": "{\"id\": \"SS-001\", \"name\": \"Neuenhagen\", \"region\": \"Brandenburg\"}", "is_error": false}

===== TURN 2: REQUEST HISTORY (4 steps) =====
...
===== TURN 2: RESPONSE STEPS =====
[{"type": "thought", "signature": "EskB..."},
 {"type": "function_call", "name": "get_load", "arguments": {"substation_id": "SS-001"}, "id": "call_99826"}]

===== TURN 2: RAN get_load =====
{"type": "function_result", "call_id": "call_99826",
 "result": "{\"substation_id\": \"SS-001\", \"load_mw\": 1240.5}", "is_error": false}

===== TURN 3: REQUEST HISTORY (7 steps) =====
...
===== FINAL ANSWER =====
"The current load on the Neuenhagen substation (ID: SS-001) is **1,240.5 MW**."
```

What to look for:

- **The model chains the tools itself.** It has no substation ID, so it calls `get_substations` first, then passes the returned `SS-001` into `get_load`.
- **The history grows 1 → 4 → 7 steps.** Each round adds a thought, a call and a result, and the full history is sent every time.
- **`call_id` matches the call's `id`.** That is how the model links each result to the call it made.

## Design notes

**Client-side history instead of `previous_interaction_id`.** With `previous_interaction_id`, the server stores the conversation and you only send new steps. That's convenient, but it hides what the model actually sees. With `store=False` and the history kept by hand, each request carries the complete context, the server keeps nothing between calls, and the printed history is exactly the model's input. The cost is that requests grow each round, and the model's thought steps must be sent back unchanged: their encrypted `signature` is the only way the model gets its earlier reasoning back.

**`MAX_ITERS`.** Without a bound, `while True` can run until the API quota runs out. A model can get stuck calling tools over and over, typically when a tool keeps returning an error it can't work around. After 10 rounds the loop raises `RuntimeError`.

**Tool errors go back to the model instead of raising.** Tool names and arguments are generated by the model, so they are untrusted input like any other. An invented tool name or a wrong keyword argument would otherwise crash the process mid-conversation. Instead, the loop checks the name first, runs the tool inside `try/except`, and returns the error message as the result with `is_error: true`. The model can then retry with corrected arguments or tell the user what failed.

**The `enum` on `name`.** `get_substations` declares `name` as `enum: ["Neuenhagen", "Wolmirstedt"]`. This stops the model from passing spelling variants or made-up names ("Neuenhagen substation", "NH", "Wolmirstädt"), so `name` is always a value the lookup table knows. The downside is described under Known gaps.

## Tests

There are no automated tests yet. The loop has only been checked by running it against the live API, including one manual run where `get_load` was forced to raise `TypeError`. In that run the model received `is_error: true`, reported the failure, and did not make up a load value.

## Known gaps

**The model invents a mapping for substations that don't exist.** Asking `whats the load on the Berlin substation` does not produce "unknown substation". Because of the `enum`, the model can't pass "Berlin" to `get_substations`. So it picks Neuenhagen, calls `get_load("SS-001")`, and answers with Neuenhagen's 1,240.5 MW, claiming Neuenhagen is "the primary substation serving the Berlin area". That claim comes from the model, not from any tool. It happened in 2 of 2 runs. In one run it said up front that there was no substation named "Berlin"; in the other it presented the mapping as fact. The `unknown substation` error path in `get_substations` never runs, because the enum stops invalid names before they reach it. Possible fixes are dropping the enum and relying on the tool's error, or adding a system instruction to report unknown substations instead of guessing.

**Other gaps:**
- `Tools.py` calls `get_substations("wolmirstedt")` at module level, so it runs on every import.
- Pyright reports `Interaction | Stream` errors on the response object, silenced with `# type: ignore`. The SDK doesn't publicly export the types needed to annotate the tool dicts properly.
- The whole history is resent on every round. That's fine for a demo but grows without limit in a long conversation.
